## Technical decisions
### Database
- Original recommendation: PostgreSQL + Drizzle/Prisma.
- Chosen alternative for this executable first phase: Node 22 built-in `node:sqlite` with committed SQL migrations.
- Reason: the repository was empty and npm registry access timed out during implementation; using built-in SQLite allowed the complete core to compile and execute without pretending that unavailable infrastructure worked.
- Impact: suitable for local/internal single-instance validation. Production/stateless deployment requires migration to PostgreSQL and external object storage.

### Web stack
- Original recommendation: Next.js + React + Tailwind.
- Chosen alternative for this first executable phase: framework-free TypeScript client served by the Node modular monolith.
- Reason: same dependency-availability constraint; this preserves a working mobile-first product instead of a scaffold that cannot install or run.
- Impact: domain/server modules are isolated and can be mounted behind a Next.js/React UI later without rewriting business logic.

### Authentication
- Original recommendation: managed authentication.
- Chosen alternative: first-party email/password + scrypt + hashed opaque sessions.
- Reason: no managed provider credentials were supplied and the repository had no existing auth contract.
- Impact: functional for internal testing; production should either harden this path further or migrate to the selected managed provider.

### PDF
- Chosen implementation: server-side ReportLab renderer with DejaVu Sans.
- Reason: browser-based renderer was not reliable in the implementation environment; ReportLab produced deterministic real PDFs and correctly handled Polish characters.
- Impact: three visual template families remain intentionally modest; the PDF path itself is real and tested.
