# CP03-O — Durable AI admission budget

The existing SQLite compatibility gateway now reserves one existing ai_requests row in a single atomic INSERT SELECT before egress. All in-flight, failed and successful attempts count toward a global UTC-day cap, including calls through newly constructed gateway instances sharing the database. AI_MAX_DAILY_REQUESTS defaults to 100 and accepts at most 10,000; this is a configurable engineering ceiling, not an approved production spending amount or empirical product policy. Existing per-call input/output token/byte/time limits remain. No assumed currency/token price is introduced; estimated_cost stays unknown. Provider-specific prices and approved monetary budget remain external configuration/acceptance prerequisites.

An exhausted budget returns AI_DAILY_BUDGET without egress; unavailable admission audit returns AI_AUDIT_UNAVAILABLE without exposing storage messages. Task/prompt/schema provenance identifiers are bounded machine tokens, preventing raw prose in those audit fields. Completion updates the reserved row instead of adding a second attempt. Interrupted calls retain AI_IN_FLIGHT and consume their reserved daily slot; they are never automatically replayed. Input content and credentials are never stored. The model/prompt/schema and input hash retain existing provenance.

This adapter is not activated in canonical PostgreSQL recruitment. The canonical local-proposal/manual confirmation fallback remains unchanged. A future native provider integration must preserve atomic admission at its PostgreSQL boundary and pass provider/privacy/financial gates before any real-data egress. No live provider, secret, paid call, schema migration or production activation is performed.

Regression uses actual loopback HTTP and temporary SQLite: competing/reconstructed gateways, in-flight admission, failed-call consumption, UTC-day renewal, unsafe metadata, admission-audit refusal and zero egress. Existing timeout/redirect/body/semantic-error contracts remain unchanged. Final actual results are recorded in IMPLEMENTATION_STATUS.md.
