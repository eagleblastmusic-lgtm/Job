# Faro implementation architecture

`src/server/index.ts` starts `createFaroApp`, a Canonical allowlist around the existing Node HTTP authentication/static server. `/api/faro/*` dispatches to authorized services; retired CV/import/EHV/billing routes return 410. Production Canonical requests return `RELEASE_GATES_OPEN` while launch gates are unresolved.

The modular monolith uses pure domain modules under `src/domain/faro` and services under `src/server/faro`. SQLite uses `JobDatabase`; the PostgreSQL18 runtime uses the shared parameterized read/write models, awaited SERIALIZABLE transactions and current-authority recovery. The authorized free Render staging explicitly selects PostgreSQL; SQLite remains the default configuration. Services reuse active membership, offer assignment and transactional helpers. Offer versions and process snapshots are distinct immutable records. Recruitment commands persist state, event and outbox together, with optimistic version checks and per-user idempotency keys.

`src/client/faro.ts` owns auth wiring, routes, requests and session cleanup. `faroViews.ts` renders domain screens; `faroUi.ts` provides shared escaped controls, labels and projections; `faroTypes.ts` declares client DTOs. `public/faro.css` scopes Night/Gold tokens and desktop/mobile layouts to the workspace. Original auth markup/styles are retained.

Migrations through 0038 cover the Canonical runtime and current-authority protections. Native PostgreSQL18 runtime/bootstrap/recovery/cutover rehearsals and desktop/mobile browser contracts are accepted on Node22/24. CW/CX and CP03-L prove free hosted PostgreSQL startup, bounded additive0038 upgrade and retained account/session/consent across an actual hosted restart. These are staging and synthetic proofs; production custody, protected durable files/authority/backups, measured RPO/RTO and independent operational acceptance remain open. Worker leases/fencing/retry/dead-letter and restart are implemented and exercised on both adapters; production scheduling stays disabled. No production cutover is performed.

Skill identity is now owned by domain/faro/skillCatalog.ts; skills.ts reexports the same public catalog API and reuses normalizeText only from historical ontology. Authored concepts are explicit and frozen; the old array index is no longer an identity producer. No legacy database records are converted or rekeyed.

CP10-F: reviewed result validity is a separate dimension from attempt lifecycle. Transactional invalidation appends original result snapshot and explanation, increments attempt revision, emits durable bilateral event, leaves process/clocks untouched. DTO current result is null for invalid or unrecorded FINALIZED validity; historical points remain explicitly labeled. No scoring override or ranking join.

CP06-I supersedes the missing local reservation mechanism: migration0030 adds durable SQLite leases and bounded claim budgets, with atomic write reservation/delivery and fencing. Two real competing processes on one SQLite file are exercised; this does not authorize multiple app deployments or prove PostgreSQL/distributed scheduling. Production scheduler remains disabled, inbox is the only delivery channel. Recovery invalidates snapshot lease tokens.

CP03-H adds 13,939 pinned Polish ESCO v1.2.1 member-skills with canonical URI/version/aliases/source attribution and hash manifest, preserving all 23 authored nodes. Candidate/learning/offer selectors search the catalog locally with bounded DOM; the authenticated session loads it once and clears it at logout. Exact skill IDs remain the matching contract; no implicit equivalence or automatic verification. Production dataset/provider approval and empirical mapping validation remain separate.
